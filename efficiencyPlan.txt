MOTHERSHIP CLI / DAEMON EFFICIENCY PLAN
=======================================

Scope: mothership-cli, mothership-daemon, and the shared mothership-common crate.
Baseline commit: 08a7fe9 (working tree clean before profiling work).


1. PROFILING BASELINE
---------------------

Profiling tests are #[ignore]d so normal test runs stay fast. Run them in release
mode, because debug SHA-256 and filesystem timings are not representative:

  cargo test -p mothership-cli --release profile_ -- --ignored --nocapture --test-threads=1
  cargo test -p mothership-daemon --release profile_ -- --ignored --nocapture --test-threads=1

Test locations:
  mothership-cli/src/profiling.rs              HTTP client reuse; shared fixtures
  mothership-cli/src/gateway.rs                profiling_tests::profile_gateway_project_lookup
  mothership-cli/src/beam.rs                   profiling_tests::profile_beam_project_lookup
  mothership-daemon/src/daemon.rs              profiling_tests::profile_content_hash_passes
                                               profiling_tests::profile_force_sync_walk

Baseline results (release, Windows, synthetic fixtures):

  Project lookup walk (20 projects, 200 dependency packages each, 4081 entries):
    miss walk (full tree)                 435 ms
    gateway: list all 20 projects         4.16 s   (20 walks, x up to 3 roots in real use)
    beam: check + resolve for 20 projects 7.90 s   (40 walks)

  HTTP calls to a local keep-alive server (200 calls):
    new reqwest::Client per call          423 us/call
    shared reqwest::Client                 33 us/call   (about 13x)

  Hashing a 256 KiB file:
    one content_hash                      107 us
    SyncBase::from_content                120 us
    current 3-hash local-edit path        314 us/edit

  Daemon force-sync walk (250 non-hidden files, node_modules included):
    force_sync_directory_static           114 ms

Not covered by a test yet (needs an integration harness): file watcher debounce and
per-event read cost, fixed sleeps in the websocket handlers, and tray polling.


2. IMPLEMENTATION PLAN
----------------------

Phase 1 - Project lookup (largest measured cost; CLI)

  Goal: one pruned walk per command instead of one per project per root.

  a. Add a shared index module in mothership-cli (for example src/project_index.rs) with:
       fn build_index(roots: &[PathBuf]) -> HashMap<String, PathBuf>
     It walks each root with max_depth(3) and filter_entry that prunes:
       - dot-prefixed directories other than .mothership
       - node_modules, target, and .git
       - AppData under USERPROFILE
     It reads .mothership/project.json once per match and records project_name -> project dir.
  b. Build the index once per command invocation and pass it into
     check_project_local_status (gateway.rs) and is_project_local / the path
     resolution in beam.rs (around lines 494 and 521). Remove the duplicate
     find_project_by_metadata functions in gateway.rs and beam.rs.
  c. Keep the search-root order (cwd, %USERPROFILE%\mothership, %USERPROFILE%) and
     first-match-wins semantics, so behavior is unchanged for existing layouts.
  d. Re-run profile_gateway_project_lookup and profile_beam_project_lookup.
     Expected: the walk count drops from N (or 2N) to 1, and the per-walk time drops
     because pruned directories are never read.

  Risk: pruning may hide a project that lives under a skipped directory. Mitigation:
  the pruned set is explicit in one place, and the change is noted in the release notes.

Phase 2 - Shared HTTP client (CLI and daemon)

  Goal: reuse connection pools and TLS state.

  a. In mothership-cli, add a process-wide client, for example
       static HTTP: OnceLock<reqwest::Client>
     and replace reqwest::Client::new() in api.rs (lines 17, 32, 51, 76, 94),
     main.rs (833, 857, 891, 910, 1032, 1073, 1186, 1252), auth.rs (67, 114, 148),
     update.rs (150, 181, 214, 269), wormhole.rs (167), and beam.rs (129, 724, 805, 848).
     Keep get_http_client(config) in main.rs for configured clients, but cache the
     built client when the config is unchanged.
  b. In mothership-daemon, reuse one client for check_server_connectivity (daemon.rs,
     around line 1133) and any other per-call builders.
  c. Re-run profile_http_client_reuse to confirm the per-call cost.

  Risk: a shared client keeps the same timeout and proxy settings, so the
  configuration must be set before first use. Check that the OnceLock is not built
  before config is loaded.

Phase 3 - Hash once per local edit (daemon)

  Goal: 3 hashes per change -> 1, and fewer content copies.

  a. Compute content_hash once in file_watcher.rs (around line 330). Store it on
     FileChangeEvent as a new field, content_hash: String.
  b. Change SyncBase::from_content (daemon.rs, around line 99) to take the hash
     as an argument: SyncBase::from_parts(hash, content). Callers that already
     have the hash stop re-hashing.
  c. Pass the hash through send_file_change_via_persistent_websocket (around line 515)
     and send_file_via_streaming instead of recomputing it.
  d. Replace crypto_hash in daemon.rs (around line 2328) and transaction.rs
     (line 244) with mothership_common::content_hash. The output format is identical
     (lowercase hex SHA-256), so the server protocol does not change.
  e. Re-run profile_content_hash_passes. Expected: the 3-hash path drops to about 1
     hash per edit (about 110 us in the test, saving about 200 us per edit).

  Risk: the hash must stay identical to what the server computes. Keep content_hash
  as the single definition and add a unit test that the two old helpers matched.

Phase 4 - Cache rift_id and stop re-reading project.json per event (daemon)

  a. Add rift_id: Option<Uuid> to TrackedProject. Load it when the project is tracked.
  b. In send_file_change_via_persistent_websocket (daemon.rs, around lines 486-500),
     read the cached value. Reload only when a rift switch is observed. The rift
     switch path already writes project.json, so update the cache there.
  c. Keep the existing error text when rift_id is missing so the failure mode is unchanged.

  Risk: a stale cache after a rift switch. Mitigation: update the cache from the same
  code path that writes project.json, and add a test for the switch.

Phase 5 - Ignore-aware force sync (daemon; performance and correctness)

  Goal: force sync should not read node_modules, target, or other ignored trees.

  a. In force_sync_directory_static (daemon.rs, around lines 1075-1125), load
     IgnoreRules once at the top level and use filter_entry, as the RiftJoined path
     already does (around line 1820).
  b. Use entry.file_type() instead of path.is_file(), path.is_dir(), and
     entry.metadata() (three stat calls per entry).
  c. Re-run profile_force_sync_walk. Expected: reads drop to the non-ignored files.

  Risk: this changes which files are sent during force sync. Confirm the default
  ignore rules cover node_modules and target before shipping, and document it.

Phase 6 - Watcher hot path (daemon)

  a. In file_watcher.rs, demote the per-raw-event log at about line 226 from info! to debug!.
  b. Before reading a file on a modify event, compare mtime and size with the last
     seen values. Skip the read when both are unchanged.
  c. Run the debounce check before hashing (around lines 330-345), so repeated
     events for the same save do not hash.
  d. Review the 250 ms EMPTY_WRITE_SETTLE sleep (around line 300). It blocks a
     blocking-pool thread. Move it to an async timer, or keep it if it is needed to
     wait for editor writes to finish.

  Risk: skipping reads on unchanged mtime can miss a same-size edit within the mtime
  resolution. Mitigation: keep a full-read fallback when the hash cache is cold.

Phase 7 - Sleeps and ordering in incoming sync (daemon; needs verification first)

  a. The handlers in daemon.rs sleep 120 ms (FileChanged, RiftDiffUpdate), 150 ms
     (RiftJoined), and 100 ms (close path). The websocket reader awaits these inline,
     which delays every message behind them.
  b. Before changing them, confirm which sleeps are ordering guards for the watcher
     echo. If they are, replace them with a path-keyed suppression window that expires
     when the matching watcher event arrives, or with a hash comparison.
  c. In RiftJoined (around lines 1800-1900), skip the write when the on-disk bytes
     already match the incoming content. This avoids a watcher echo for no change.

  Risk: this is the most behavior-sensitive phase, because it affects echo suppression
  and could cause sync loops. Do it last, and test with two daemons syncing the same rift.

Phase 8 - Tray polling (daemon; low priority)

  a. system_tray.rs (around lines 163-185): replace the periodic try_recv polling and
     menu rebuilds with event-driven updates, or rebuild only when status changes.
  b. Measure before and after with a short integration run. No unit-level profile yet.


3. ORDER AND DEPENDENCIES
-------------------------

  Phase 1 and Phase 2 are independent and give the largest gains; do them first.
  Phase 3 before Phase 4, because both touch the send path.
  Phase 5 is independent of the others.
  Phase 6 depends on Phase 3 (the hash moves into the event).
  Phase 7 is last, because it is the most sensitive to sync behavior.
  Phase 8 is optional.


4. VALIDATION
-------------

  Per phase:
    cargo build -p mothership-cli -p mothership-daemon
    cargo test -p mothership-cli -p mothership-daemon
    cargo test -p mothership-cli -p mothership-daemon --release profile_ -- --ignored --nocapture
  Compare each profile result against the baseline in section 1.

  Behavior checks:
    - Project listing and beam output are unchanged for the same layout.
    - Force sync sends the same file set minus ignored paths.
    - Two-daemon sync shows no echo loops after Phase 7.

  Working-tree hygiene: commit each phase separately so a regression can be reverted.
